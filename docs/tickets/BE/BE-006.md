# BE-006 — Lock down CORS

**Type:** Security
**Epic:** BE — Backend correctness & safety
**Affects:** `backend/src/job_assistant/main.py`
**Priority:** P1
**Status:** `PLANNED`

## Summary
The API allows requests from every origin.

## Current behaviour
```python
origins = ["*"]

app.add_middleware(
    CORSMiddleware,
    allow_origins=origins,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

Two problems:

1. `allow_origins=["*"]` lets any website call the API from a visitor's browser. Combined with the
   missing rate limit (BE-005), any page a user visits can burn the DeepSeek budget.
2. `allow_origins=["*"]` together with `allow_credentials=True` is an invalid combination per the
   CORS spec — browsers reject the response. It signals copied-from-a-snippet configuration.

Note what CORS does and does not do here: a Chrome extension with `host_permissions` is **not**
governed by CORS the way a web page is, so the extension keeps working under a strict allowlist.
CORS is browser-enforced only — it is not an authentication mechanism, and this ticket should not
be mistaken for one.

## Why it matters
Open CORS on an endpoint that spends money is a real (if low-severity) vulnerability, and the
`*` + `credentials` combination is a well-known review catch.

## Proposed scope
- Replace `*` with an explicit allowlist read from configuration (BE-007), including the dev
  origins needed for local work and the future web client from MOB-001.
- Set `allow_credentials=False` unless cookie auth is genuinely introduced.
- Restrict `allow_methods` to `["POST", "GET", "OPTIONS"]` and `allow_headers` to
  `["Content-Type", "X-Request-ID", "Authorization"]` (the latter two as they are introduced).
- Add security headers (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy`) — either `fastapi.middleware` or the `secure` package.
- Verify the extension still works after the change (it should; confirm rather than assume).
- Document how to add an origin.

## Acceptance criteria
- [ ] A request with `Origin: https://evil.example` does not receive an
      `Access-Control-Allow-Origin` header for that origin.
- [ ] The extension's analysis flow still works end to end after the change.
- [ ] `allow_credentials` is `False` unless cookie auth exists.
- [ ] Allowed origins are configuration-driven, not hardcoded.
- [ ] README explains how to add an allowed origin.

## Notes
Do this together with BE-007, since both replace hardcoded configuration with environment values.
