# BE-010 — Request correlation and token/cost tracking

**Type:** Observability
**Epic:** BE — Backend correctness & safety
**Affects:** `backend/src/job_assistant/`
**Priority:** P2
**Status:** `PLANNED`

## Summary
There is no way to tie a user-visible failure to a server-side log line, and no record of how many
tokens each request consumed or what it cost.

## Current behaviour
Requests are anonymous. When something fails, the user sees an error and there is nothing to search
logs for. DeepSeek returns a `usage` object on every response, and it is discarded — so neither the
per-request cost nor the running total is known, which also means BE-005's budget cap has nothing
to count.

## Why it matters
Correlation ids and cost accounting are the two observability features that most convincingly say
"this person has operated a service." Token accounting is also a prerequisite for the spend cap,
so this ticket is partly a dependency of BE-005.

## Proposed scope
- Generate a request id (UUID4) per request, or accept an incoming `X-Request-ID` header; store it
  in a `contextvars.ContextVar` so it appears in every log line without being threaded through
  function arguments.
- Return the id in an `X-Request-ID` response header and in the error body (BE-002).
- Read `response.usage` from DeepSeek and log `prompt_tokens`, `completion_tokens`, and
  `total_tokens` per request along with summed latency.
- Maintain a running daily token/cost counter that BE-005's budget guard consults.
- Expose a `GET /stats` endpoint (protected, or dev-only) returning requests today, tokens today,
  estimated cost today, and error rate.
- Add latency timers around the guard call and the model call separately, so the cost of the
  third-party guard is measurable rather than assumed.
- Add a test asserting the same request id appears in the log record and the response header.

## Acceptance criteria
- [ ] Every response carries an `X-Request-ID` header.
- [ ] All log lines for one request share that id.
- [ ] Token usage from the model response is logged and accumulated.
- [ ] `GET /stats` reports request count, tokens, and estimated cost for the current day.
- [ ] Guard latency and model latency are logged separately.
- [ ] The counter is reset/rotated at day boundaries in a defined way.

## Notes
Keep the counter in-process for now and say so explicitly — the honest framing is "sufficient for a
single-instance demo, would move to Redis or the database for multi-instance." Do not imply
durability that does not exist.
