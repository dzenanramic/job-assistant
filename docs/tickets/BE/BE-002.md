# BE-002 — Never crash on bad model output; return a clean error contract

**Type:** Bug / Reliability
**Epic:** BE — Backend correctness & safety
**Affects:** `backend/src/job_assistant/services/analyzer.py`
**Priority:** P0
**Status:** `PLANNED`

## Summary
`analyze_cv()` calls the model and then blindly `json.loads()` the result. Any failure — malformed
JSON, a network error, a model timeout, a schema mismatch — propagates as an unhandled exception
and the user sees a raw HTTP 500.

## Current behaviour
```python
def analyze_cv(job_desc, cv):
    print(job_desc, cv)
    is_prompt_safe = is_injection(cv=cv)

    if is_prompt_safe:
        result = ai_response(job_desc=job_desc, cv=cv)
        result = json.loads(result)      # raises on malformed output
        return result
    else:
        raise HTTPException(status_code=400, detail="Security check failed: ...")
```

Failure modes with no handling:

| Failure | Today's result |
|---------|----------------|
| Model returns prose instead of JSON | `json.JSONDecodeError` → 500 |
| Model returns JSON missing `score` | FastAPI `ResponseValidationError` → 500 |
| DeepSeek API unreachable / times out | `openai.APIConnectionError` → 500 |
| TypeSafe guard unreachable | `TypeSafeError` → 500 |
| Model returns `score: "high"` instead of an int | Pydantic validation error → 500 |

Even though `json_object` response format is requested, the model is not guaranteed to produce a
valid payload, and the transport can fail independently of the model.

## Why it matters
This is the single most likely thing a reviewer will hit when they run the project — LLM
endpoints fail intermittently by nature. A 500 with a stack trace reads as "unfinished"; a
clean, typed error reads as "this person has run something in production."

## Proposed scope
- Define an error contract in the response body, e.g.
  `{"error": {"code": "UPSTREAM_INVALID_RESPONSE", "message": "...", "requestId": "..."}}`.
- Wrap the model call in `try/except` for `openai.APIError`, `APIConnectionError`,
  `APITimeoutError`, and `RateLimitError`; map to `502`/`503`/`429` with clear messages.
- Parse defensively: attempt `json.loads`, and on failure retry **once** with a corrective
  follow-up message before giving up.
- Validate the parsed payload against `AnalysisResponse` explicitly rather than relying on
  FastAPI's post-return validation, so a bad shape produces a 502 and not a 500.
- Clamp/coerce `score` into `0..100`; reject or repair out-of-range values.
- Never return a provider error message verbatim to the client (it can contain account details).
- Add a FastAPI exception handler so unhandled exceptions return the same JSON shape.

## Acceptance criteria
- [ ] A stubbed client returning `"not json"` yields a `502` with `UPSTREAM_INVALID_RESPONSE`, not a 500.
- [ ] A stubbed timeout yields `503`/`504` with a retryable message.
- [ ] A payload missing `score` yields a clear 4xx/5xx, not a Pydantic traceback.
- [ ] A `score` of `-5` or `150` never reaches the client unclamped.
- [ ] No exception traceback is ever returned in the HTTP response body.
- [ ] Covered by tests (QA-001).
