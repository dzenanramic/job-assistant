# BE-009 — Single source of truth for response models

**Type:** Refactor
**Epic:** BE — Backend correctness & safety
**Affects:** `backend/src/job_assistant/schemas/schemas.py`, `services/deepseek_client.py`
**Priority:** P2
**Status:** `PLANNED`

## Summary
The required JSON shape is described **twice** — once as a Pydantic model and once as a hand-written
schema embedded in the system prompt. The two are maintained independently and will drift.

## Current behaviour
`schema.py` defines:
```python
class AnalysisResponse(BaseModel):
    score: int
    strengths: List[str] = Field(default_factory=list)
    gaps: List[str] = Field(default_factory=list)
    suggestions: List[str] = Field(default_factory=list)
    flags: List[str] = Field(default_factory=list)
```

and the system prompt in `deepseek_client.py` separately contains:
```
FORMAT IZLAZA (strogo JSON): {"score": <broj 0-100>, "strengths": [...], ...}
```

Nothing keeps these in sync, and Pydantic is already capable of generating the schema. There is
also no `min_length`/`max_length` on the list fields, so the prompt's "3-5 items" instruction is
unenforced, and `score` has no `ge=0, le=100` constraint even though the prompt claims that range.

## Why it matters
Schema drift between prompt and validator is a classic LLM-app bug: you change the model, forget
the prompt, and start emitting 502s. Generating one from the other is a small change that shows
you understand the failure mode.

## Proposed scope
- Generate the prompt's JSON schema from the Pydantic model, e.g. `AnalysisResponse.model_json_schema()`,
  and interpolate it into the system prompt. One definition, two consumers.
- Add real constraints to the model: `score: int = Field(ge=0, le=100)`,
  `strengths: list[str] = Field(min_length=1, max_length=8)`, and similar bounds for the other
  lists.
- Decide and document what happens when the model returns 2 strengths or 9 — truncate, accept, or
  retry. Do not leave it undefined.
- Move the system prompt out of Python source into a template file or a config value, so prompt
  changes are reviewable as prompt changes.
- Consider using the provider's structured-output/JSON-schema mode if available, instead of only
  `response_format={"type": "json_object"}`.

## Acceptance criteria
- [ ] The JSON schema in the prompt is generated from `AnalysisResponse`, not written by hand.
- [ ] There is exactly one place to change when a field is added or renamed.
- [ ] `score` outside `0..100` is rejected or clamped by validation, not by luck.
- [ ] List length bounds are enforced and their violation behaviour is documented.
- [ ] A test asserts the prompt contains the model's schema and stays in sync when a field is added.

## Notes
The current prompt is written in Bosnian while the rest of the codebase is in English. That is a
legitimate product choice (it targets regional job boards) but it should be a deliberate, noted
one — mix the languages inside a single file and a reviewer will assume it was accidental.
