# QA-002 — CI pipeline on every push

**Type:** DevOps
**Epic:** QA — Testing & CI
**Affects:** repo root (`.github/workflows/`)
**Priority:** P1
**Status:** `PLANNED`

## Summary
Nothing runs automatically. There is no `.github/` directory, so a push can break the import paths
(BE-001) or the schemas without anyone noticing — which is exactly what already happened.

## Current behaviour
No CI configuration of any kind. The only record of a change being checked is that it was committed.
`backend/src/job_assistant/__pycache__/*.pyc` being tracked in git is direct evidence that no check
ever runs: a lint or ignore step would have caught it immediately.

## Why it matters
A green CI badge in the README is one of the cheapest, most visible credibility signals a portfolio
repo can have. It also converts "I think it works" into "it is verified on every commit" — and it
makes the whole rest of this backlog enforceable rather than aspirational.

## Proposed scope
- Add `.github/workflows/ci.yml` triggered on push and pull request.
- **Backend job:** install `uv`, `uv sync`, run `ruff` (lint + format check), run `pytest` with
  coverage (QA-001). No API keys required — the suite must stub all providers.
- **Extension job:** `npm ci`, run ESLint and the extension tests (QA-004).
- Run both jobs in parallel; a failure in either fails the workflow.
- Add a `pyproject.toml` `[tool.ruff]` config and an ESLint config so the lint steps are meaningful.
- Add a status badge to the root `README.md` (DOC-001).
- Make the pipeline reproducible from a clean checkout and record the exact local equivalent
  commands in the README, so CI failures can be reproduced without pushing.
- Consider a third job later for Docker build validation (ARCH-002) and deployment (ARCH-003).

## Acceptance criteria
- [ ] A push triggers lint + test for both backend and extension.
- [ ] The workflow fails on a red test or a lint error (verify by pushing a deliberate failure).
- [ ] No real API key is required or present — secrets are not needed for the test job.
- [ ] CI completes in a few minutes and is reproducible locally with documented commands.
- [ ] A badge in the README reflects the current status.

## Notes
Order: QA-001 first. A CI pipeline with no tests is a green badge that proves nothing, and a
reviewer who notices that will trust the badge less than no badge at all.
