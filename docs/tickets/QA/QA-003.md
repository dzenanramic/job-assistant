# QA-003 — Extension automated tests + build tooling

**Type:** Testing / Extension
**Epic:** QA — Testing & CI/CD
**Affects:** `extension/`
**Priority:** P3

## Summary
The extension (`extension/`) has **no test** ("`Error: no test specified`"), loads vendored
`node_modules` at runtime (`pdf.mjs`, `marked`, `dompurify` are imported straight from
`./node_modules`), and imports work only because the manifest page is a module. This is fragile
and untested.

## Proposed scope
- Introduce a **test runner** (e.g. Vitest/Jest) with unit tests for the pure logic:
  `text-utils` (normalize per marker/config), adapter extraction logic (MS-001) with a mock DOM,
  markdown→sanitized-HTML rendering (SEC-004), and file-utils PDF text extraction with a fixture.
- Add a **bundler/webpack build** step for the popup that inlines vendor libs so the extension no
  longer relies on reading `node_modules` at runtime (also gets a proper CSP in SEC-004).
- Wire these into CI (QA-002).

## Acceptance criteria
- [ ] `npm test` runs and covers text-utils, adapters, sanitizer, and PDF fixture parsing.
- [ ] Popup ships as a bundled artifact; no runtime `node_modules` import.
- [ ] Extension checks run in container CI.
- [ ] Fixtures (sample HTML page, sample PDF) committed for deterministic tests.

## Notes
Extension tests are rarer and impressive. MS-001's adapter abstraction (MS-001) is what makes the
extraction logic testable at all — build on it.
