# OBS-002 — Centralized error handling & API error contract

**Type:** Backend feature
**Epic:** OBS — Observability, logging, errors
**Affects:** `backend/`, `extension/`
**Priority:** P2

## Summary
Errors bubble up raw (e.g. an OpenAI failure would surface as a generic `500` with an ugly stack;
the extension catches with `error.message`). There is no consistent error shape, no `Problem
Details`-style contract, and no mapping of known failure modes (429, timeout, model error, input
too long) to meaningful messages.

## Proposed scope
- Add a **global exception filter** (NestJS `ExceptionFilter`) producing a consistent error body:
  `{ status, code, message, traceId, details? }`.
- Map the known failure modes to codes: `RATE_LIMITED`, `INPUT_TOO_LONG`, `AI_PROVIDER_ERROR`,
  `TIMEOUT`, `VALIDATION_ERROR`, `NOT_FOUND`.
- Ensure stack traces are not returned to clients (log server-side instead — see OBS-001).
- Update the extension to render the structured error (code + friendly message) rather than raw
  `error.message`.

## Acceptance criteria
- [ ] Every response (success/error) from the backend has a consistent shape.
- [ ] Known model/provider failures map to stable error codes with friendly client messages.
- [ ] Stack traces/CLIENT internals are never exposed in responses.
- [ ] Extension shows a clean error state referencing the code/traceId.

## Notes
This is a "clean API design" ticket — pairs well with SEC-004 and OBS-001.
