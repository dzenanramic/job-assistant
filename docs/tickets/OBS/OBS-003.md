# OBS-003 — Config management & secrets hygiene (`@nestjs/config`)

**Type:** Backend feature / tech debt
**Epic:** OBS — Observability, logging, errors
**Affects:** `backend/`
**Priority:** P2

## Summary
The API key and port are read directly via `process.env` (`jobs.service.ts`, `main.ts`), and
`@nestjs/config` is already a dependency but is **not wired in**. There is no `.env` schema
validation, no fail-fast if `DEEPSEEK_API_KEY` is missing, and the model name/base URL are
hardcoded in the service.

## Proposed scope
- Wire up **`ConfigModule`** as a global module loading `.env`, and read config through typed
  config objects/services.
- **Validate** env at boot (`class-validator`/Joi): fail fast on missing/invalid `DEEPSEEK_API_KEY`.
- Centralize model name, base URL, limits (SEC-003), rate-limit values (PERF-001) in config.
- Ensure `.env` stays git-ignored (already listed) and no key is committed.

## Acceptance criteria
- [ ] App fails to start with a clear message when `DEEPSEEK_API_KEY` is missing/invalid.
- [ ] No raw `process.env` access remains in feature code (moved behind config).
- [ ] Config values (model, caps, limits) are overridable, not hardcoded.
- [ ] `.env.example` documents all required/optional vars.

## Notes / CV value
Clients care about "secrets handling" a lot. This is also a prerequisite for the CI e2e tests
(QA) to run against a configured instance.
