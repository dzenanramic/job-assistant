# SEC-002 — Input validation on the API surface (DTO + pipe)

**Type:** Security / Backend feature
**Epic:** SEC — Security & prompt-injection defense
**Affects:** `backend/`
**Priority:** P1

## Summary
The backend currently accepts **anything** in the request body. `CreateJobDto` has two plain
`string` fields with no decorators; `POST /jobs` calls the AI before any validation. There is **no
`ValidationPipe`**, no `class-validator` / `class-transformer`, and no length/size limits. The
`app.controller.ts` `POST /` also accepts a raw `{ text }` and just logs it. This is both an
abuse/cost vector (see SEC-003/PERF) and a prompt-injection surface (SEC-001).

## Proposed scope
- Enable a **global `ValidationPipe`** (`whitelist: true`, `forbidNonWhitelisted: true`) in
  `main.ts`.
- Annotate `CreateJobDto` with `class-validator` rules:
  - `text` (job description) and `cvText`: `@IsString()`, `@IsNotEmpty()`, and `@MaxLength(...)`
    with a sane cap (see SEC-003).
  - Reject request bodies containing unexpected keys (whitelist/forbid).
- Add validation for any new site/tenant identifier fields introduced by MS-002 (format, allowed
  charset).
- Make the type of `text`/`cvText` explicit and non-optional (they currently default to `''`).

## Acceptance criteria
- [ ] Sending a body with a non-string or over-long field returns `400` with a clear message.
- [ ] Unknown/extraneous body keys are rejected.
- [ ] Empty `text`/`cvText` are rejected (or given a definable default) rather than silently
  prompting with blanks.
- [ ] Existing happy-path flow still works (no regression).
- [ ] Unit test covers representative invalid bodies.

## Notes
Tightly linked to SEC-001 (guardrails need predictable, bounded input) and SEC-003 (size limits).
`api.js` in the extension should remain compatible — validation should only reject truly invalid
payloads.
