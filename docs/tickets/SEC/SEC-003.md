# SEC-003 — Input size & cost limits (token/length caps)

**Type:** Security / Backend feature
**Epic:** SEC — Security & prompt-injection defense
**Affects:** `backend/`
**Priority:** P2

## Summary
CVs and job descriptions are sent to DeepSeek **unbounded**. A malicious or accidental multi-MB
blob (e.g. a parsed PDF that includes base64 or a whole page dump) inflates token count, raises
cost, and risks the model throwing on input-too-long. There is currently no ceiling.

## Proposed scope
- Enforce a **max character length** on `text` and `cvText` (e.g. 30–60k chars; exact cap decided
  in implementation) at the DTO/validation layer — ties into SEC-002.
- Add a **token/byte estimate** guard in the service **before** calling the model, aborting with a
  413 or a clear 400 when over budget.
- Optionally chunk/truncate per an explicit strategy rather than a hard failure (decision recorded
  in the ticket during implementation — default recommendation: reject clearly-abusive sizes,
  truncate gracefully near the model's context limit).
- Report the actual token usage returned by the API when available for observability (see OBS).

## Acceptance criteria
- [ ] Requests exceeding the character cap return a clear 4xx.
- [ ] Service estimates tokens/bytes and refuses to call the model when over budget.
- [ ] A documented decision exists for truncate-vs-reject behaviour.
- [ ] Tests confirm oversized payloads do not reach the model client.
