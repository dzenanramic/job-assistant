# SEC-005 — Authentication & tenant isolation for real usage

**Type:** Security / Feature
**Epic:** SEC — Security & prompt-injection defense
**Affects:** `backend/`
**Priority:** P3 (foundational but lower if no real users yet)

## Summary
There is currently **no authentication** — anyone who can reach the endpoint can burn the API key's
credits and read responses. For a portfolio product it demonstrates strong backend practice to add
a lightweight auth layer, especially once multi-tenant (MS-002) and persistence (DATA-001) exist.

## Proposed scope
- Introduce an **API-key / bearer-token scheme** for the extension → backend calls (store the key
  in extension `storage.chrome` settings rather than hardcoded/localhost).
- Protect `/jobs` with an auth **guard** (NestJS `CanActivate`).
- Once tenants exist, bind the presented key to a tenant and enforce data scoping (see MS-002).
- Store keys hashed; provide rotation/revocation endpoints.
- Do **not** roll a custom login/session system unless a UI truly needs it; API keys are the
  right-sized first step.

## Acceptance criteria
- [ ] Requests without a valid credential are rejected (401/403).
- [ ] Each credential is bound (or not) to a tenant/scope; scoping enforced.
- [ ] Keys stored hashed; revoke/rotate supported.
- [ ] `.env` docs updated; extension configurable to send the key.

## Notes
Keep scope lean. If you never intend real multi-user, an API key alone (no accounts) is a clean,
interviewable deliverable.
