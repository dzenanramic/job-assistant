# SEC-004 — Safe handling and rendering of AI output (XSS defence)

**Type:** Security / Extension hardening
**Epic:** SEC — Security & prompt-injection defense
**Affects:** `extension/`, `backend/`
**Priority:** P2

## Summary
The extension renders the model's markdown as HTML. It already runs the result through
**DOMPurify** (`extension/api.js`) — good. But there are remaining gaps: (1) the DeepSeek output
is only sanitized in the extension, not at the backend boundary, and (2) fields scraped from job
pages (MS-001 structured fields like title/company) are not all sanitized with equal care. Because
the model is *itself* a prompt-injection target (SEC-001), its output must never be trusted enough
to carry markup back into the DOM unfiltered.

## Proposed scope
- **Server-side:** sanitize/normalize the AI markdown response **on the backend** before returning
  it (defense in depth — don't rely on the client).
- **Client-side:** keep DOMPurify sanitization on all model output that is injected via
  `innerHTML`, and extend it to any new structured fields rendered by the popup (title, company,
  links).
- Never set `innerHTML` with a full-page or unscoped source; prefer text rendering where markup
  is not needed (already partly done) and allow-listed element/attribute config for whitelisted
  rich output.
- Add a Content-Security-Policy to the extension pages that still allows the app to function.

## Acceptance criteria
- [ ] All model-provided content rendered via `innerHTML` is sanitized server-side **and**
  client-side.
- [ ] A crafted model output containing `<script>` or event-handler attributes renders inert.
- [ ] CSP header/meta present on extension pages; no console violations.
- [ ] Sanitization unit-tested with known XSS payloads.

## Notes
This is the classic **"never trust LLM output"** portfolio point; combine SEC-004 with SEC-001 to
show an end-to-end security story (input → prompt → output → DOM).
