# MS-002 — Multi-tenant architecture for the backend

**Type:** Epic / Feature
**Epic:** MS — Multi-site support
**Affects:** `backend/`
**Priority:** P1 (explicit ask)

## Summary
Design the backend so it can serve **multiple sites / tenants** (and eventually signed-in users)
in an isolated, per-tenant way, instead of being a single global `POST /jobs` endpoint.

## Background / Why
"Served by one site" is a limitation you explicitly called out. Recruiters reading "multi-tenant"
on a resume signals database design, isolation, and API design. Even before there are real paying
customers, structuring the data model and endpoints around a tenant/origin identifier now avoids
a costly re-architecture later and makes the app demonstrable as a real product.

## Proposed scope
- Define a **tenant/origin concept**: each request to AI-analysis should be attributed to a source
  site or organization, identified via a header (e.g. `X-Site-ID` / `X-Tenant-ID`) or an API key.
- Refactor **API contract** so requests carry `{ siteId, jobListing, cvText }` instead of
  `{ text, cvText }` (aligns with MS-001's structured JobListing).
- Introduce dependency-injected **site configuration** (per-site system prompt, per-site feature
  flags, per-site rate limits) rather than one hardcoded prompt string in `jobs.service.ts`.
- All new endpoints and queries are scoped by tenant; no cross-tenant reads leak.

## Acceptance criteria
- [ ] A request without a valid tenant/origin identifier is rejected (or assigned a default) intentionally.
- [ ] AI prompts are per-site configurable (system prompts stored per tenant).
- [ ] Data model carries a tenant/org foreign key (once DATA-001 adds persistence).
- [ ] No endpoint returns data not scoped to the requesting tenant.
- [ ] Rate limits (PERF-001) are applied per tenant, not globally.

## Out of scope
- Real subscription/billing-grade tenant onboarding (that is SEC-005/MS-004).

## Notes / CV talking point
Pair MS-002 with DATA-001 (persistence) to tell a complete "multi-tenant SaaS database schema"
story in interviews.
