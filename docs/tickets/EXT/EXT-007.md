# EXT-007 — Remove dead dependencies and add a build step

**Type:** Chore / Tooling
**Epic:** EXT — Extension robustness
**Affects:** `extension/package.json`, `extension/`
**Priority:** P2
**Status:** `PLANNED`

## Summary
`package.json` declares three dependencies and has no build step. `pdfjs-dist` is not actually used
— the library is vendored into `extension/lib/` — and `dompurify` and `marked` are installed but
never imported. `npm test` is still the scaffold failure script.

## Current behaviour
```json
"dependencies": {
  "dompurify": "^3.4.13",
  "marked": "^18.0.9",
  "pdfjs-dist": "^4.4.168"
},
"scripts": {
  "test": "echo \"Error: no test specified\" && exit 1"
}
```

Verified against the source:

- `dompurify` and `marked` appear only in a **commented-out** line in `api.js`. Never imported.
- `pdfjs-dist` is never imported either — `file-utils.js` imports `./lib/pdf.mjs`, a vendored copy.
- `node_modules/` exists but nothing at runtime depends on it; the extension loads plain ES modules
  directly.
- `manifest.json` is named "Job Finder Assistant" while the repo, README, and UI title all say
  "Job Assistant". The description ("Extracts visible text from the current page") describes an
  earlier, much smaller extension.

So `npm install` is currently a no-op step that a reviewer will run and then wonder about, and the
manifest metadata does not describe what the product does.

## Why it matters
Unused dependencies and a placeholder test script are small signals that add up. Extension metadata
is also what a user sees in `chrome://extensions` and the Web Store listing.

## Proposed scope
- Remove `dompurify`, `marked`, and `pdfjs-dist` from `dependencies` if EXT-002 is solved with
  `textContent` (recommended), or move whichever are genuinely needed to a real build pipeline.
- Decide and document how the vendored `lib/pdf.mjs` is obtained and how it is updated — record the
  pdf.js version in a comment or a small `lib/README.md`, since a vendored file with no provenance
  is a maintenance trap.
- Add a minimal build or at least a validation script: `lint` (ESLint with the extension globals),
  `test` (see QA-004), and a `zip` script for packaging.
- Fix `manifest.json` metadata: consistent name, a description of what the extension actually does,
  a real version bump policy, and an `icons` entry (currently none, so Chrome shows a default
  puzzle piece).
- Add `default_locale` / i18n only if you intend to translate — otherwise skip, but note the
  decision (the UI is English while the prompt is Bosnian).
- Consider adding `minimum_chrome_version` given the `sidePanel` API.

## Acceptance criteria
- [ ] `package.json` lists only dependencies the code actually uses.
- [ ] The extension still loads and works after removal.
- [ ] `manifest.json` name and description match the real product; icons are present.
- [ ] `npm run lint` and `npm test` exist and do something real.
- [ ] The pdf.js version and its update procedure are documented.

## Notes
If EXT-002 keeps rich-text rendering, then `marked` and `DOMPurify` become genuinely used and should
stay — but they must actually be imported. Right now they are dead weight either way.
