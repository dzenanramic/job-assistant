# EXT-003 — Detect API failures instead of rendering `undefined`

**Type:** Bug
**Epic:** EXT — Extension robustness
**Affects:** `extension/api.js`, `extension/popup.js`
**Priority:** P1
**Status:** `PLANNED`

## Summary
The API helper treats every HTTP response as a success and returns the parsed body regardless of
status. When the backend returns an error, the UI renders `undefined` in the score field rather
than explaining what went wrong.

## Current behaviour
```javascript
const response = await fetch(API_URL, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(payload),
});

const result = await response.json();
console.log("THIS IS RESULT IN SENDTEXTTOAPI", result);
return result;
```

Problems:

- `response.ok` is never checked. A `400`, `422`, `429`, or `502` body (e.g. FastAPI's
  `{"detail": "..."}`) is returned as if it were a valid `AnalysisResponse`.
- `popup.js` then does `score.innerText = sendText.score` → renders `undefined`, and
  `sendText.strengths.map(...)` → throws `TypeError`, caught by the generic handler and shown as a
  raw JS error message.
- `response.json()` throws on a non-JSON body (a proxy error page, a 503 HTML page), producing a
  confusing parse error instead of "the server is unavailable".
- There is no timeout, so an unresponsive backend leaves the button disabled forever.
- The error path overwrites `.result-content` with `textContent`, which destroys the result markup
  permanently — subsequent successful analyses render into a gutted container.

## Why it matters
This is what a reviewer sees when the backend is not running, which is likely to be the very first
thing they experience. "Error: Failed to fetch" in place of a result looks broken; a clear
"Can't reach the analysis service — is the backend running on port 8000?" looks deliberate.

## Proposed scope
- Check `response.ok`; on failure, extract `detail`/`error.message` if present and throw a typed
  error carrying the status code.
- Guard `response.json()` — read as text first, then parse, and fall back to a readable message.
- Add an `AbortController` timeout (e.g. 60 s — analysis is genuinely slow) and surface a timeout
  message.
- Distinguish network failure (`TypeError: Failed to fetch`) from an HTTP error and from a timeout,
  with a different message for each.
- Handle `429` specifically: read `Retry-After` (BE-005) and tell the user how long to wait.
- Fix the error rendering so it does not destroy the result markup — use a dedicated error element
  that is hidden on success.
- Remove the leftover `console.log` lines.

## Acceptance criteria
- [ ] Backend down → clear "cannot reach the service" message, not `undefined` or a raw TypeError.
- [ ] A `422` from validation shows the backend's message to the user.
- [ ] A `429` shows a wait time.
- [ ] A non-JSON error body does not produce a parse error.
- [ ] A hung request times out with a message and re-enables the button.
- [ ] After an error, a subsequent successful analysis renders correctly in full.
- [ ] No `console.log` remains in `api.js`.

## Notes
Best tested together with EXT-005, which makes the backend URL configurable — pointing it at a dead
port is the quickest way to exercise every branch here.
