# EXT-002 — Stop injecting model text with `innerHTML`

**Type:** Security / Bug
**Epic:** EXT — Extension robustness
**Affects:** `extension/popup.js`
**Priority:** P1
**Status:** `PLANNED`

## Summary
Model output is inserted into the DOM as HTML string concatenation with no sanitization. The
`DOMPurify` and `marked` dependencies that would fix this are installed but never used.

## Current behaviour
```javascript
strengths.innerHTML = sendText.strengths.map((el) => `<li>${el}</li>`).join("");
gaps.innerHTML        = sendText.gaps.map((el) => `<li>${el}</li>`).join("");
suggestions.innerHTML = sendText.suggestions.map((el) => `<li>${el}</li>`).join("");
```

`sendText.*` are raw strings produced by the model. The model's input includes the **scraped job
page**, which is attacker-controlled web content. A job ad can therefore try to steer the model
into emitting markup into these arrays.

This is not theoretical: a `<img src=x onerror=...>` string returned inside a `gaps` array becomes
live DOM in the extension's side panel, which shares an origin with the extension's other pages and
can read `chrome.storage`.

The comment in `api.js` shows the sanitization step was intended and never wired up:
```javascript
// const purifiedText = DOMPurify.sanitize(marked.parse(result));
```

## Why it matters
This is a genuine stored-XSS-to-privileged-context path, and the fix is a few lines. "The LLM's
output is untrusted input" is a strong point to raise in an interview — but only if the code
reflects it.

## Proposed scope
- **Prefer text nodes over HTML.** These are plain list items with no markup requirement — build
  them with `document.createElement("li")` and `textContent`, which makes injection impossible by
  construction. This is the right fix here; sanitization is the fallback for when markup is truly
  needed.
- If any field genuinely needs rich text, use `marked` + `DOMPurify.sanitize` with a strict
  allowlist, then assign the sanitized result — never the raw model string.
- Apply the same treatment to `score` and any future field (currently `innerText`, which is
  already safe — keep it that way, and do not "upgrade" it to `innerHTML`).
- Add a Content-Security-Policy to the extension pages blocking inline script and remote script.
- Have the backend validate and normalize these fields too, so the client is not the only defense.
- Add a test that feeds `<img src=x onerror=alert(1)>` through the render function and asserts the
  output is inert text.

## Acceptance criteria
- [ ] No model-provided value reaches `innerHTML`; list rendering uses `textContent`.
- [ ] A payload of `<script>alert(1)</script>` in any field renders as visible literal text.
- [ ] An `<img onerror>` payload does not execute.
- [ ] A CSP is present on the side panel page and the UI still works.
- [ ] If `marked`/`DOMPurify` remain installed, they are actually used — otherwise remove them
      (EXT-007).
- [ ] A test covers the injection case.

## Notes
The general rule worth stating in an interview: *any string that passed through an LLM is untrusted
input, even if you "wrote" the prompt.* The model is a transform over attacker-controlled data, not
a sanitizer.
