# EXT-001 — Handle unsupported, empty, and oversized CV files

**Type:** Bug / UX robustness
**Epic:** EXT — Extension robustness
**Affects:** `extension/popup.js`, `extension/file-utils.js`
**Priority:** P1
**Status:** `PLANNED`

## Summary
The CV upload path assumes every selected file is a valid, text-bearing PDF. Any other file —
unreadable PDF, scanned image PDF with no text layer, or a huge file — produces a confusing failure
or a silent bad analysis.

## Current behaviour
```javascript
const handleAddCv = async () => {
  const fileName = cvInput.files[0]?.name || "file";
  const file = await extractPdfText(cvInput.files[0]);
  cvText = file;
  document.getElementById("uploadTitle").textContent = "CV added ✓";
  document.getElementById("uploadHint").textContent = fileName;
};
```

Problems:

- **No try/catch.** A malformed or encrypted PDF makes `extractPdfText` reject; the rejection is
  unhandled, the UI stays on "Choose your CV", and nothing explains why.
- **Empty result treated as success.** A scanned PDF (images only) parses without error and
  yields an empty string. The UI shows "CV added ✓" and the backend then receives an empty CV.
- **No size limit.** A 200 MB PDF is read fully into memory and parsed page by page in the side
  panel.
- **No file type check.** `.pdf` is set on `accept`, but `accept` is only a picker hint — a user can
  still choose any file via "All files", and there is no validation on the `change` event.
- **Failure is invisible.** There is no error state in the UI for a failed upload.

Note: the misleading "PDF, DOC, DOCX" label and the wide `accept` list have already been corrected
to PDF only. This ticket is about the remaining runtime handling, not the label.

## Why it matters
Uploading a CV is the first thing a reviewer does. A scanned PDF (very common — many people have
image-based CVs) currently produces a confident-looking analysis of nothing, which is worse than an
error message.

## Proposed scope
- Wrap the parse in `try/catch`; on failure show a clear, human message ("This PDF could not be
  read. Try re-exporting it from Word or Google Docs.") and reset the upload label.
- Validate on selection: MIME type / extension, and a size cap (align with BE-004's limit).
- Detect the empty-text case: if the extracted text is shorter than a sensible minimum, report
  "No text found — this looks like a scanned PDF" instead of showing success.
- Keep the parsed `cvText` in `chrome.storage.session` (or `local`) so closing the side panel does
  not lose the CV (see EXT-006).
- Clear `cvInput.value` after handling, so re-selecting the **same** file fires `change` again —
  currently it will not, which is a real papercut when a user fixes their CV and re-uploads.
- Show a "CV added ✓" state only after a successful, non-empty parse.

## Acceptance criteria
- [ ] Selecting a corrupt PDF shows an inline error and does not set `cvText`.
- [ ] Selecting a scanned, image-only PDF shows "no extractable text", not success.
- [ ] Selecting a file above the size cap is refused with a clear message.
- [ ] Re-selecting the same filename after an error works.
- [ ] Analyze is disabled (or warns) when no valid CV is loaded.
- [ ] `cvText` is not lost when the side panel is closed and reopened.

## Notes
DOC and DOCX support is deliberately **out of scope** here. If you want it later, the cleaner move
is parsing on the backend (MOB-002) where `python-docx` is a one-line dependency, and then both the
extension and the web client get it for free.
