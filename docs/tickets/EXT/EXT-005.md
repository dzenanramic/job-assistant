# EXT-005 — Make the backend URL configurable

**Type:** Feature / Config
**Epic:** EXT — Extension robustness
**Affects:** `extension/api.js`, `extension/popup.html`
**Priority:** P2
**Status:** `PLANNED`

## Summary
The backend URL is hardcoded to a localhost address. The extension cannot be pointed at a deployed
backend without editing source and reloading.

## Current behaviour
```javascript
// api.js
const API_URL = "http://127.0.0.1:8000/jobs";
```

This has three consequences:

1. To use a hosted backend (ARCH-003), the user must edit a source file and reload the unpacked
   extension in `chrome://extensions`.
2. The root `README.md` still documents the backend as `http://localhost:3000/jobs` (NestJS-era) while
   `api.js` points at `127.0.0.1:8000`. The two disagree, and `127.0.0.1` vs `localhost` are not
   interchangeable for CORS purposes (BE-006).
3. `manifest.json` already requests the `storage` permission, which is exactly what is needed here —
   the permission is granted but unused.

## Why it matters
Any reviewer who wants to try the extension has to read the source to find out what it talks to.
A settings field turns a hardcoded demo into something that can be pointed anywhere, and it is the
prerequisite for the deployed version in ARCH-003.

## Proposed scope
- Add a settings section in the side panel: a text field for the API base URL, with validation
  (must be `http`/`https`, must parse as a URL) and a "Test connection" button hitting `/health`
  (BE-011).
- Persist to `chrome.storage.sync` so it survives reloads and follows the user across devices.
- Default to the current localhost value so existing behaviour is unchanged on first run.
- Add a "Reset to default" action.
- Support a **build-time** default as well (e.g. a `config.js` generated from an environment
  variable), so a packaged build can ship pointing at the hosted backend without user setup.
- Update `manifest.json` `host_permissions` to include whatever deployed origin is used — note that
  a Chrome extension cannot obtain host permission for an arbitrary user-entered URL at runtime
  without `optional_host_permissions`, which may require requesting permission dynamically. Decide
  and document which approach is used.
- Fix the README's stale port reference (DOC-001).

## Acceptance criteria
- [ ] The API URL can be changed from the UI and persists across reloads.
- [ ] An invalid URL is rejected with a clear message before any request is sent.
- [ ] "Test connection" reports success or a specific failure against `/health`.
- [ ] Default behaviour on a fresh install is unchanged.
- [ ] A build can ship a default URL without user configuration.
- [ ] The chosen host-permission strategy is documented, including its limitations.

## Notes
The host-permission question is the interesting part of this ticket — worth understanding properly,
since it is the reason many extensions cannot simply "point anywhere".
