# EXT-008 — Site adapter registry with a generic fallback

**Type:** Feature / Refactor
**Epic:** EXT — Extension robustness
**Affects:** `extension/chrome-utils.js`, `extension/text-utils.js`
**Priority:** P3
**Status:** `PLANNED`

## Summary
Site-specific extraction is expressed as two parallel lookup tables — a domain list in one file and
a marker table in another — with no shared interface and no fallback. Adding a fourth site means
editing two files correctly and hoping the markers are right.

## Current behaviour
`chrome-utils.js` holds a domain map whose values are identical to its keys:
```javascript
const sites = { linkedin: "linkedin", dzobs: "dzobs", helloworld: "helloworld" };
const site = Object.keys(sites).find((domain) => tab.url?.includes(domain));
```
`text-utils.js` holds a separate marker table keyed by those same strings:
```javascript
const siteMarkers = {
  dzobs:      { start: "objavi oglas", end: "prijavi se" },
  linkedin:   { start: "about the job", end: "" },
  helloworld: { start: "", end: "pogledaj profil kompanije" },
};
```

Two files, two representations of "which sites are supported", no single place to add one. The
extraction strategy is also purely textual — `indexOf` on the lowercased body text — which breaks
the moment a site changes its wording.

## Why it matters
This is the architectural question a reviewer will ask about: "how would you add Indeed?" Today
the honest answer is "edit two files and guess at a magic string." A registry answers it cleanly,
and it is a genuinely good thing to talk through in an interview.

## Proposed scope
- Define a single `SiteAdapter` shape: `{ id, matches(url), extract(document) -> JobListing }`.
- One registry keyed by adapter id; `chrome-utils.js` resolves the adapter and calls it, so adding
  a site is a one-file change.
- Return a **structured** `JobListing` instead of a raw string:
  `{ title, company, location, seniority, description, postedAt, url }`. Prefer DOM selectors
  (`[itemprop]`, `main`, `article`) over text markers where possible; keep markers only as a
  fallback within an adapter.
- Add a **generic adapter** used when no site matches: best-effort extraction from
  `main`/`article`/`[itemprop]`, with a documented quality caveat.
- Log which adapter handled the request.
- Send the structured listing to the backend rather than one text blob (coordinates with MOB-001's
  contract).
- Keep the existing three sites working as the first three adapters — this is a refactor, not a
  rewrite.

## Acceptance criteria
- [ ] Adding a new site requires editing exactly one file.
- [ ] Each of the three current sites is implemented as an adapter with the same interface.
- [ ] An unknown site uses the generic adapter and returns something usable, without throwing.
- [ ] Extraction returns a structured `JobListing`, not a raw string.
- [ ] Adapters are unit-testable against saved HTML fixtures (QA-004).
- [ ] The adapter used for each request is logged.
