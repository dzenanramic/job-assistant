# EXT-004 — Warn when the page is not a supported job site

**Type:** Bug / UX
**Epic:** EXT — Extension robustness
**Affects:** `extension/chrome-utils.js`, `extension/text-utils.js`, `extension/popup.js`
**Priority:** P1
**Status:** `PLANNED`

## Summary
On any site that is not one of the three known job boards, the extension silently scrapes the
entire page and sends it for analysis. On every other site, the per-site trimming is skipped and
`normalizeText` throws.

## Current behaviour
```javascript
const site = Object.keys(sites).find((domain) => tab.url?.includes(domain));
// ... returns { text, site }  — site is undefined on unknown domains

// text-utils.js
export const normalizeText = (text, site) => {
  const markers = siteMarkers[site];            // undefined for unknown sites
  const startIndex = markers.start ? ...        // TypeError: Cannot read properties of undefined
```

Two distinct failures:

1. **Unknown site → crash.** `siteMarkers[undefined]` is `undefined`, and the very next line reads
   `markers.start`. The error surfaces through the generic catch in `popup.js` as a raw TypeError.
2. **Known site, missing marker → silent garbage.** If a supported site redesigns and the marker
   string (e.g. `"prijavi se"`) disappears, `indexOf` returns `-1`, the code falls back to
   `0`/`text.length`, and the **entire page** — navbar, footer, cookie banner, sidebar, unrelated
   links — is sent to the model. The analysis is quietly degraded and nothing indicates a problem.

The second case is the more damaging one: it fails silently, and marker strings are brittle by
nature because they depend on a site's marketing copy.

Also, `manifest.json` declares `host_permissions` for exactly three domains, so the extension
cannot even inject into other sites outside those patterns — but `activeTab` is also granted, which
allows a user-initiated injection anywhere. The two mechanisms disagree about intent.

## Why it matters
The most likely reviewer path is: install the extension, open it on some random page, click
Analyze. Today that produces a TypeError. A clear "This page isn't a supported job posting — open a
job ad on LinkedIn, dzobs, or helloworld" makes the limitation look intentional rather than broken.

## Proposed scope
- Handle the unknown-site case explicitly: show a message naming the supported sites instead of
  throwing.
- Give `normalizeText` a safe default and never index `siteMarkers[site]` without a check.
- Detect a **missed marker** on a known site: if the marker is not found, do not silently use the
  whole page. Either fall back to a conservative generic extraction (main/article content) or
  warn the user that extraction quality is reduced.
- Log which strategy was used, so a broken adapter is diagnosable.
- Reconcile `host_permissions` and `activeTab`: either support the generic path everywhere, or
  restrict to the declared domains and say so.
- Show the detected site in the panel so the user can see what was recognized.
- Return a minimum-length check: if the extracted text is implausibly short for a job ad, warn
  rather than analyze.

## Acceptance criteria
- [ ] Clicking Analyze on an unsupported site shows a helpful message, not a TypeError.
- [ ] A supported site with a missing/changed marker does not send the whole page verbatim.
- [ ] The panel displays which site was detected.
- [ ] Extraction that produces suspiciously little or too much text shows a warning.
- [ ] `normalizeText(text, undefined)` does not throw (unit test).

## Notes
The deeper fix is EXT-008 (adapter registry with a generic fallback). This ticket is the cheap
version that removes the crash and the silent degradation now; EXT-008 is the design that makes it
extensible later. Doing EXT-004 first is fine and does not block EXT-008.
