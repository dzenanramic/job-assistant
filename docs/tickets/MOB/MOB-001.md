# MOB-001 — Web client foundation and shared contract

**Type:** Epic / Feature
**Epic:** MOB — Mobile & web client
**Affects:** new `web/`, `backend/`
**Priority:** P2
**Status:** `PLANNED`

## Summary
Add a mobile-friendly web client that talks to the same backend, so the product is usable without
installing a Chrome extension. This is the foundation ticket: agree the API contract and stand up a
client, before adding features.

## Background / Why
The extension only works on desktop Chrome, only on three job boards, and only for users willing to
load an unpacked extension. A phone-friendly page removes all three constraints and is a much
stronger CV line — it demonstrates designing one API for two very different clients.

The architectural point worth making: **the mobile client cannot reuse the extension's approach.**
The extension scrapes the DOM of the page the user is already viewing. A web page has no access to
another origin's DOM. So the client must send something else — raw pasted text (this ticket), a
file upload (MOB-002), or a URL for the backend to fetch (MOB-003). Designing that now is the whole
value of this ticket.

## Current API contract
```jsonc
// POST /jobs
{ "text": "<job description>", "cvText": "<cv>" }
```

This shape assumes the client has already extracted both texts and has nowhere to put job metadata.
It does not fit a mobile flow, and it will not fit a structured `JobListing` (EXT-008).

## Proposed scope
- **Design the shared contract first.**
  - Rename `cvText` → `cv_text` with a backward-compatible alias so the shipped extension keeps
    working (BE-004).
  - Add an optional `cv_id` so a client can upload a CV once and reference it on repeat analyses
    (depends on MOB-002).
  - Add optional structured job metadata: `{ job: { title, company, location, url, description } }`,
    while still accepting the flat `text` field for the extension. Document precedence.
  - Introduce `/api/v1/` versioning now, before there is a second client to break. Keep `/jobs`
    working as a deprecated alias for one release.
- **Build the client** under `web/` — a responsive single page that works at 360 px wide:
  - paste a job description into a textarea, paste or upload a CV, tap Analyze, see the result;
  - the same result shape as the extension (score, strengths, gaps, suggestions, flags);
  - loading, empty, and error states — the extension's UI (skeleton, aria-live) is a good reference;
  - readable on a phone: large tap targets, no horizontal scroll, no hover-only affordances.
- **Choose a deliberately small stack.** Plain HTML/CSS/JS with ES modules is enough for this scope
  and avoids a build pipeline; a small Vite + React app is also reasonable if you want the
  experience on your CV. Either way, justify the choice in the README rather than defaulting to the
  heaviest option.
- **Share the schema, do not duplicate it.** The contract should have one definition. Generate
  TypeScript types from the FastAPI OpenAPI schema (BE-011) rather than hand-writing them, and
  commit the generated file with the command that produces it.
- Keep the client stateless for now: no accounts, no history (MOB-005 covers that).

## Acceptance criteria
- [ ] A page at a local URL performs a full analysis from pasted text on a 360 px viewport.
- [ ] The same backend endpoint serves both the extension and the web client, unchanged in
      behaviour for the extension.
- [ ] `cv_text` is accepted; the extension's existing `cvText` payload still works.
- [ ] Endpoints are versioned under `/api/v1/` with `/jobs` still working.
- [ ] Client types are generated from the OpenAPI schema, not written by hand.
- [ ] Loading, empty, and error states all render correctly on mobile.
- [ ] CORS allows the web origin (BE-006).
- [ ] README documents how to run the client and why the stack was chosen.

## Notes
Implementation order after the contract work: this ticket, then MOB-002 (upload), then MOB-004
(auth) before the page is ever publicly reachable — MOB-003 and MOB-005 are optional after that.
