# MOB-004 — Auth for public clients

**Type:** Security / Feature
**Epic:** MOB — Mobile & web client
**Affects:** `backend/`, `web/`, `extension/`
**Priority:** P3
**Status:** `PLANNED`

## Summary
There is no authentication. That is tolerable while the backend only listens on localhost; it stops
being tolerable the moment a public web page can reach it.

## Current behaviour
`POST /jobs` accepts anything from anyone. There is no credential, no identity, and no way to
distinguish one caller from another — which is also why BE-005 can only rate limit by IP, and why
that limit is both easy to evade and unfair to users behind a shared NAT.

## Why it matters
Auth is the gate on shipping anything public (ARCH-003), and it is the prerequisite for per-user
history (MOB-005), per-caller budgets, and any meaningful multi-tenant story. "I can explain why I
did **not** build full accounts, and what I built instead" is a stronger answer than either extreme.

## Proposed scope
- Choose the lightest scheme that fits, and write down the reasoning:
  - **Anonymous session token** — the backend issues a signed, expiring token on first visit; no
    signup. Enough to rate limit per user and attach history.
  - **API keys** — issued to known clients; good for the extension, awkward for a public web page.
  - **Email magic link** — a real account boundary with no password handling; more work, better
    history story.
  Recommend starting with the anonymous session token plus optional upgrade to magic link later.
- Implement as a FastAPI dependency (not middleware), so routes opt in explicitly and the
  authenticated caller is available to the handler.
- Store issued tokens/keys **hashed**, with an expiry and a revocation path. Never store a raw
  token.
- Move the rate limiter's key from IP to caller identity (BE-005), falling back to IP for
  unauthenticated requests.
- Bind the spend/token budget (BE-005, BE-010) to the caller rather than to the process.
- Reject unauthenticated requests to paid endpoints with `401`, using the error contract (BE-002).
- Keep the extension working: it should obtain and store a token in `chrome.storage` rather than
  hardcoding one.
- Do **not** build a password system. Password storage, reset flows, and session management are a
  large surface that adds risk without adding CV value here.

## Acceptance criteria
- [ ] Paid endpoints require a valid credential and return `401` without one.
- [ ] Tokens expire and can be revoked; revoked tokens are rejected.
- [ ] Only hashed credentials are persisted.
- [ ] Rate limits and spend budgets are keyed by caller, not by IP, for authenticated traffic.
- [ ] The web client and the extension both obtain credentials without user-visible setup.
- [ ] A secret-manager or config path exists for the signing key (BE-007), never a default.
- [ ] The chosen scheme and the rejected alternatives are documented in the README.

## Notes
Keep the scope deliberately small. The value here is the reasoning — why API keys, why not
passwords, what the threat model actually is — not the amount of code. A large hand-rolled auth
system is more likely to impress negatively than positively.
