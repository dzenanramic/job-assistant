# MOB-002 — CV upload and parsing on the backend

**Type:** Feature
**Epic:** MOB — Mobile & web client
**Affects:** `backend/`, `web/`, `extension/`
**Priority:** P2
**Status:** `PLANNED`

## Summary
Move CV parsing to the backend so any client can upload a file, rather than every client needing to
parse PDFs locally.

## Current behaviour
CV parsing happens in the browser: `extension/file-utils.js` loads a vendored pdf.js and extracts
text page by page, then sends the resulting string as `cvText`. Consequences:

- Only the extension can accept a CV file. A phone browser would have to ship an entire PDF parser.
- **DOCX is not supported at all**, and PDF only. The UI has already been corrected to say "PDF"
  only, so the limitation is now honest but still a limitation.
- The extension carries a vendored `lib/pdf.mjs` + `lib/pdf.worker.mjs` (~large files) that no other
  client can reuse, with no recorded version (EXT-007).
- PDF parsing quality is entirely the client's problem, so scanned/image PDFs silently yield an
  empty string (EXT-001).

## Why it matters
This is the change that makes a mobile client practical, and it is the single best argument for the
"one backend, multiple clients" design. It also gives the project something concrete to say about
file handling — an area where Python's ecosystem is genuinely strong.

## Proposed scope
- Add `POST /api/v1/cv` accepting `multipart/form-data` with a PDF or DOCX file:
  - validate MIME type, magic bytes, and size (align with BE-004's cap);
  - enforce a page/character cap after extraction;
  - parse with `pypdf` for PDF and `python-docx` for DOCX;
  - detect the empty/scanned-PDF case and return a clear `422` rather than an empty CV.
- Add `GET /api/v1/cv/{cv_id}` returning the extracted text, and an expiry policy for stored CVs
  (see below).
- **Decide and document the storage policy.** Options:
  - *stateless*: return the extracted text immediately, store nothing — simplest, safest for
    personal data, but the client must resend the text every time;
  - *short-lived cache*: store extracted text keyed by an opaque id with a TTL (e.g. 1 hour),
    in memory or SQLite — better UX, still no long-term retention.
  Recommend the short-lived cache with an explicit TTL, and state the retention rule in the README.
  Do not store CVs indefinitely without a stated reason and a deletion path.
- Update the **web client** to upload a file, showing extraction progress and the resulting
  character count so the user can confirm the parse worked.
- **Update the extension to use the same endpoint** so both clients share one parser — this removes
  the vendored pdf.js from the extension and closes EXT-001's scanned-PDF problem for both clients
  at once.
- Sanitize/normalize extracted text (collapse whitespace, strip control characters, cap length).
- Apply the same injection guard to uploaded CV text (BE-008).
- Add tests with fixture files: a normal PDF, a scanned PDF, a DOCX, a corrupt file, and an
  oversized file (QA-001).

## Acceptance criteria
- [ ] `POST /api/v1/cv` accepts a PDF and a DOCX and returns extracted text.
- [ ] A corrupt file returns `422` with a helpful message, not a 500.
- [ ] A scanned/image-only PDF returns a clear "no extractable text" error.
- [ ] An oversized file is rejected before parsing.
- [ ] The web client can upload a CV and see the analysis without any local parsing.
- [ ] The extension uses the same endpoint and no longer ships pdf.js.
- [ ] Storage/TTL policy is implemented, documented, and has a deletion path.
- [ ] Uploaded CV text passes through the injection guard.
- [ ] Tests cover every case above with fixtures.

## Notes
Moving parsing server-side slightly increases the backend's cost footprint (CPU, memory) and its
data-handling obligations — a CV is personal data. Both are acceptable, but they should appear in
the README's security section as a conscious tradeoff, not be discovered by a reviewer.
