# MOB-005 — Analysis history

**Type:** Feature
**Epic:** MOB — Mobile & web client
**Affects:** `backend/`, `web/`
**Priority:** P3
**Status:** `PLANNED`

## Summary
Nothing is stored. Every analysis is discarded the moment it is returned, so a user cannot look back
at previous jobs, compare scores, or track how their CV edits affected results.

## Current behaviour
The backend is completely stateless. `POST /jobs` computes a result and returns it; there is no
database, no ORM, no migrations, and no models package (BE-001 corrected a dangling `models.schemas`
import — note that this is a *schemas* package, not a data model). The only copy of a result is in
the browser tab that requested it.

## Why it matters
This is what turns a one-shot tool into something a job seeker returns to over weeks. It also
introduces the parts of backend engineering a portfolio project most often lacks: schema design,
migrations, indexes, and data lifecycle — highly relevant to almost any backend role.

## Proposed scope
- **Schema design.** A real domain model, not a blob table:
  - `users` (from MOB-004) — or anonymous sessions if that is the chosen scheme.
  - `cvs` — uploaded CV, extracted text, hash, created/expires timestamps.
  - `job_postings` — title, company, location, url, description, source site.
  - `analyses` — links a CV to a job posting, with the score, the structured result, the model name,
    token usage, and status (pending/succeeded/failed).
  - Indexes on `(user_id, created_at)` and on the CV/job foreign keys; a unique constraint where it
    is meaningful (e.g. one analysis per user+CV+job unless explicitly re-run).
- **Migrations** from day one — Alembic with SQLAlchemy, or Django-style migrations if you go that
  route. Never `create_all()` in application startup as the only mechanism.
- **Database choice:** SQLite is entirely reasonable for a portfolio project and needs no hosting;
  Postgres via Compose (ARCH-002) is the more transferable answer. Pick one, document why, and keep
  the repository layer thin enough that switching is not a rewrite.
- **API surface:** `GET /api/v1/analyses` (paginated list), `GET /api/v1/analyses/{id}`,
  `DELETE /api/v1/analyses/{id}`, and `POST /api/v1/analyses/{id}/rerun`. All scoped to the calling
  user — a user must never be able to read another's row.
- **Async write path:** record the request first with status `pending`, then update on completion,
  so a crashed request leaves a visible `failed` row instead of nothing. This is also the groundwork
  for a proper job queue later.
- **Data lifecycle:** CVs are personal data. Define a retention period, provide deletion, and
  document both. Deleting a user must delete their CVs and analyses.
- **Web client:** a history list showing date, job title, company, and score, with a detail view and
  a re-run action. Make it usable at 360 px — this is the mobile surface, not an afterthought.
- **Tests:** schema constraints, user-scoped reads (an explicit cross-user access test that must
  404), deletion cascade, and pagination edges (QA-001).

## Acceptance criteria
- [ ] Analyses, CVs, and job postings are persisted with a real schema and migrations.
- [ ] A user can list, open, re-run, and delete their own past analyses.
- [ ] A user **cannot** read or delete another user's analysis (test proves it).
- [ ] Deleting a CV removes dependent analyses or anonymises them, per the documented policy.
- [ ] A failed analysis leaves a `failed` row with a reason, not a silent gap.
- [ ] Retention policy is implemented and documented.
- [ ] The history UI is usable at 360 px.
- [ ] Migrations run automatically on deploy, idempotently.
- [ ] No PII appears in application logs (BE-003).

## Notes
Deliberately last: it is the largest ticket here and it depends on MOB-004 for identity. Do not
start it before the stateless product works end to end — a database on top of a broken analysis path
just gives you a broken analysis path with a schema.
